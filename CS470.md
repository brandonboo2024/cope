# CS470 changes (branch `cs470`)

This fork reruns COPE for the CS470 project. Small model: Qwen2.5-1.5B-Instruct (local). Large model: DeepSeek Flash (`deepseek-flash`, hosted).

## Experiments
| Recipe | What it is | Origin |
|---|---|---|
| `recipes/cs470/math500_cope.yaml` | COPE on the first 50 MATH-500 problems | **reproduction**: released `collaborative` approach, unchanged logic |
| `recipes/cs470/math500_small.yaml` / `_big.yaml` | Each model alone, temperature 0, COPE's solution prompt | baselines (new `direct` approach) |
| `recipes/cs470/mbpp_cope.yaml` | COPE on the first 50 eligible MBPP test tasks | **reimplementation** from the paper (not in the release) |
| `recipes/cs470/mbpp_small.yaml` / `_big.yaml` | Each model alone, one greedy solution | baselines |
| `recipes/cs470/{math500,mbpp}_big_plan.yaml` | DeepSeek writes COPE's guideline, then solves with it (COPE stage 3 for every task) | same-model control (new `big_plan` approach) |

## Run
From the CS470 workspace root (`nix develop .#cope` selects `external/cope/venv`):
```sh
set -a; . ./.env.local; set +a; export OPENAI_API_KEY=$OPEN_API_KEY
nix develop .#cope --command bash -c 'cd external/cope &&
  python scripts/test_time_compute.py recipes/cs470/math500_cope.yaml &&
  python scripts/grade_math.py outputs/cs470/math500_cope.jsonl &&
  python scripts/run_mbpp.py recipes/cs470/mbpp_cope.yaml'
```
One-time venv setup on NixOS:
- Build the venv: `python3 -m venv venv; venv/bin/pip install vllm accelerate datasets fastapi hf_transfer latex2sympy2==1.9.1 'openai>=1.45.0' pebble word2number; venv/bin/pip install --no-deps -e .`
- Point Triton's bundled NVIDIA tools at Nix's glibc loader. They are generic Linux binaries that NixOS will not run as-is:
  `for f in ptxas ptxas-blackwell cuobjdump nvdisasm; do patchelf --set-interpreter "$(patchelf --print-interpreter "$(readlink -f "$(which python3)")")" venv/lib/python3.11/site-packages/triton/backends/nvidia/bin/$f; done`

Outputs land in `outputs/cs470/`: per-task `*.jsonl` and a `*.graded.json` summary.

## Stage logs (from 18 Oct 2026)
The runs above saved only each task's final answer, so a stage that rejected left no trace of Qwen's attempts. COPE now logs every stage:
- Each task's record has a `stages` list (a JSON string for maths). Each entry holds the stage (`1a`, `1b`, `2a`, `2b`, `3`), the exact messages sent, every output, finish reasons and output tokens.
- For voting stages, `vote` records the extracted answers, the counts, the majority, its share, the threshold, the decision and the chosen attempt. For code, it records which candidates passed the public tests and, after grading, the hidden tests.
- `grade_math.py` grades every attempt. `run_mbpp.py` runs every candidate on the hidden tests. Both write `stage_checks` to the summary: per stage, wrong accepts, rejected stages that had a right answer, and capped outputs.
- `scripts/trace_cs470.py <bench> <dir>` renders a logged run with every attempt.

`outputs/cs470/logged/` is a fresh logged run of COPE on the same 50 + 50 tasks. Its answers are new samples, so a few tasks may end at a different stage than in the original run.

## Scoring
- **MATH-500** (`scripts/grade_math.py`): COPE's bundled Qwen2.5-Math grader. The final answer is extracted (boxed, or "final answer is") and compared numerically or symbolically with the reference.
- **MBPP** (`scripts/run_mbpp.py`):
  - The final program passes all hidden MBPP-ET tests (about 102 per task).
  - Generated code runs in bubblewrap with no network, the standard library only, and a 30 s limit.
  - A task is eligible only if MBPP's reference solution passes its public and MBPP-ET tests. This is checked before any model runs; tasks 11–60 all pass.

## Deviations from the release, and why
1. **Package versions.** The release pins `vllm==0.6.3` and `transformers<4.48`, which cannot run on the RTX 5070 Ti (Blackwell). The venv uses vLLM 0.31.0, torch 2.13.0+cu130 and transformers 5.17.0, and installs COPE with `--no-deps`.
2. **DeepSeek thinking off.** `big_thinking: false` (default) sends `thinking: disabled`. DeepSeek V4.1 Flash thinks by default, and the proposal pilot ran with it off.
3. **Qwen chat template.** The recipes set `custom_chat_template: null`, as the upstream Qwen recipes do. The config's default is a Llama-3 template, which the released `collaborative.yaml` would otherwise apply to Qwen.
4. **`direct` approach** (`src/sal/search/direct.py`). These are the single-model baselines; `test_time_compute.py` skips loading vLLM when only the large model is used.
5. **MBPP** (`src/sal/search/code.py`, `scripts/run_mbpp.py`). This follows the paper (Sec. 4, 5.2):
   - It uses the same stages, temperatures and prompt templates as maths.
   - A stage accepts if at least one candidate passes MBPP's public tests, with a passing one picked at random.
   - The executor and planner system prompts are quoted from the paper. The small model's goal prompt is adapted from the maths one, since the paper gives none.
   - Models see the standard MBPP prompt: the description plus the public tests.
   - Code is taken from the answer's code blocks that define something (`def`, `class`, `import`). Usage or self-test blocks are dropped. An earlier last-block rule wrongly failed correct answers; `scripts/regrade_mbpp.py` re-scores saved outputs.
   - The released stage-2 quirk is kept: if stage 1 fails, the small goal is passed as `None`.
6. **Eager mode.** The recipes set `enforce_eager: true` (a new config option), so vLLM skips torch.compile and CUDA graphs. On this NixOS machine torch.compile fails: it needs a Blackwell `ptxas` that the venv lacks. This affects speed, not outputs. The flake also sets `TRITON_LIBCUDA_PATH`, because Triton otherwise calls `/sbin/ldconfig`.
7. **Sample size.** 50 tasks per benchmark (the paper uses all 500), matching the proposal pilot.
